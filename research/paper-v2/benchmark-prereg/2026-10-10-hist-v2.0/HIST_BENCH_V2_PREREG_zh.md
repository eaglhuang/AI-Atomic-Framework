## 0. 一句話

HIST v1.x 回答的是「ATM 提交時會不會弄丟東西」。HIST-v2 要回答 ATM 真正獨有的部分：**多個 agent 從同一個 base 同時改同一個檔時，相容的修改能不能一起進去而不必排隊，衝突的修改會不會被正確拒絕而不是被亂合**，並且把代價和 file_lock 放在同一張圖上比。

## 1. 核心主張與終點

| 主張 | 白話 | 主要終點（逐題、逐 run） | 什麼結果算「不支持」 |
|---|---|---|---|
| **C1 不遺失、不損毀** | 已確認提交（ack）的效果最後都在檔案裡，檔案沒有多出、少掉或打亂的行 | 遺失效果數、損毀檔數、結構違規數；失敗 run／總 run | 任何一個遺失或損毀＝§5.7 反例，照實報告、停止規則照舊 |
| **C2 相容的都進得去，而且不必排隊** | A、B 類題目（B 類同區可合併是主要證據），所有 proposal 都落地，最終 bytes 與參考答案逐位元相同；多份 proposal 真的在同一批、同一 base 上合成 | 正確合併率；實際 batch size 分布；正確完成量／秒；從送出到終態的延遲 p50／p95／p99 | 相容題被誤拒、或 batch size 恆為 1、或吞吐與延遲和 file_lock 沒有差別（後者照實寫成「在該條件下與 file_lock 收斂」） |
| **C3 衝突的會被正確拒絕** | C 類（真正衝突）題目，只有一方落地，另一方收到結構化的拒絕收據；不會出現兩邊混在一起的結果 | 正確拒絕率；錯誤合併（mis-merge）數；拒絕理由分布 | 任何一筆錯誤合併 |

三個主張都只在「已測工作負載」範圍內成立，不外推成一般保證。

## 2. 抽題工具：全部候選都測，工具只負責分類與事先標答案

### 2.1 原則（文一 2026-10-10 決定）

- **不挑題、不刪題。** 所有候選配對（與 3–4 份的延伸組）全部都測。抽題工具只做兩件事：**分類**，以及**事先寫好每一題的測試目的與正確答案**。
- 分類與標答案**只使用 PR 本身的特徵**：`git merge-file`／`git merge` 的結果、改到的行範圍、hunk 是否重疊或相鄰、檔案類型、是否新建／刪除／改名檔、測試能不能跑（base validity）。工具**不執行任何臂**，也不讀任何 run 的結果。
- **只有技術上跑不起來的才排除**（例如 checkout 失敗、PR head 已抓不到、檔案不是文字檔、patch 無論如何都無法放到共同 base 上），每一筆都記理由碼，與分類結果一起封存，分母完整。
- 分類規則、參數與輸出在任何 run 開始前凍結並記 SHA-256。
- 結果**依類別分開報**，簡單的題目不會稀釋困難的題目；全部合併的總數只當次要數字。

### 2.2 來源

| 來源 | 內容 | 用途 |
|---|---|---|
| 開發集（dev） | 既有六專案（Django、SymPy、xarray、pytest、Sphinx、FastAPI）、時間窗 2024-01-01～2025-12-31 的**全部候選配對**（PR #242 挖掘：考慮 2,641 對，其中 1,205 對因 base 漂移在 v1.x 被排除——在 v2 改以 rebase 前 head 或三方合併放回共同 base，不再排除） | 冒煙測試、pilot、主跑 |
| 未見資料測試集（held-out） | **時間 held-out**：同六專案、2026-01-01～2026-09-30（UTC，含端點）合併的 PR 的全部候選。**專案 held-out（D1）**：`pallets/flask` 與 `psf/requests`，merged_at 落在 2024-01-01～2026-09-30（UTC，含端點）的全部候選，集合標 `held-out-project`。兩專案與 dev 沒有共同 PR。跨窗配對規則見下一段 | 本預先登記的分類階段只標籤、不跑臂。修正版與 harness 凍結後，held-out 只跑一次，單獨報告 |

- held-out 與 dev **不得共用任何 PR**：時間窗本身不重疊；跨窗配對（一方在 2025、一方在 2026）歸到 held-out 時，若其中一個 PR 已出現在 dev，該配對記為 `shared-pr-with-dev` 並歸入 dev 的「跨窗」附加層，不進 held-out（這是分組規則，不是丟掉）。
- 開發過程中找到的反例與修正，只能用 dev 驗證「修好了」；「修正能推廣」只能由 held-out 回答。

### 2.3 一道「題目」是什麼

- 一道題＝同一個專案、同一個共同 base、同一個目標原始碼檔上的 **2 份**（主體）或 **3–4 份**（延伸組，次要）PR patch。
- 共同 base＝各 PR base 的 merge-base（沿用 v1.x §3.1）。某份 patch 無法直接套到共同 base 時，依序嘗試：(a) 該 PR 在對方合併前的最後一版 head（v1.1 選項 P）；(b) 以 `git merge-file` 三方合併放回共同 base（有衝突就保留衝突，供類別 C 使用）。兩者都不行才記 `unapplicable-to-common-base` 排除，並另報這類的數量。
- 每份 patch 對應一個模擬 agent；送出順序＝原始 commit 順序（以各 PR head commit 的 committer 時間排序；同時間以 PR 編號排序）。

### 2.4 分類、測試目的與正確答案（在任何 run 之前寫好）

寫入類別（互斥，每題恰好一類）：

| 類別 | 判定（全部決定性，只看 PR 本身） | 測試目的 | 正確答案 |
|---|---|---|---|
| **A 不相交／不衝突** | 改到不同區域（hunk 之間距離 > 3 行），`git merge-file` 乾淨 | 一般寫入測試 | 兩邊效果都保留；最終檔案＝git 合併結果，逐位元相同 |
| **B 同區域但可合併** | hunk 重疊或相鄰（距離 ≤ 3 行），`git merge-file` 乾淨，且依任一順序合併結果相同 | **合成測試** | 所有 proposal 都落地；最終檔案＝git 合併結果，**逐位元相同** |
| **C 真正衝突** | `git merge-file` 回報衝突 | **拒絕測試** | 只有一方落地（或某幾方的相容子集），其他收到結構化拒絕；最終檔案＝base 加上完整的落地方，**不得出現混合** |
| A′／B′ 附加層 | 兩邊改法完全相同（identical）；合併乾淨但順序不同結果不同（order-dependent） | 單列描述 | 依該層各自定義，不併入 A／B／C |
| D 新建／刪除／改名檔 | 任一份 patch 新建、刪除或改名目標檔 | 寫入安全測試（ATM steward 目前不能建立新檔） | 不遺失、不損毀；被拒絕時須為 fail-closed，單列報告 |

語意旗標（與寫入類別正交，每題都有）：

| 旗標 | 判定 | 語意終點 |
|---|---|---|
| **S 可評估** | 兩個 PR 都有 gold 測試，且通過 STALE 的 base validity（gold 測試在 base 上失敗、加上自己的 code patch 後通過） | 照 §6 評分 |
| **N 無可跑測試** | 沒有 gold 測試、base validity 不成立、或是 rebase 前 head（不是最終合併的程式碼） | **只做寫入安全**，語意標「不可評估」，不計為 0 |

- 文一列的四類對應為：(1)＝A、(2)＝B、(3)＝C、(4)＝旗標 N。
- 標籤是**操作性定義**：以 Git 的文字合併為準。ATM 採保守 context 規則時，可能把 Git 判為可合併的 B 類拒絕，這會被計為「誤拒」並照實報告，不改標籤。
- 另記分層 O1（同一 hunk）／O2（相鄰 1–3 行）／O3（不同區域）、patch 大小（hunk 數、目標檔行數）與是否為 rebase 前 head，作為分析用的共變數，不用來刪題。

### 2.5 技術排除理由碼（只有這些）

`head-unavailable`、`checkout-failed`、`binary-or-non-utf8`、`unapplicable-to-common-base`、`base-env-unbuildable`（只影響語意終點時，改標旗標 N，不排除）、`shared-pr-with-dev`（只用於分組，見 §2.2）。每筆記錄候選 id、理由碼與診斷訊息。大小不是排除理由：很大的題目照跑，超過期限記為逾時並報告。

### 2.6 相依性：全部保留，分析時處理

- 因為全部候選都測，同一個 PR 會出現在多道題。每道題記 `cluster_id`：以「共用 PR」把題目連成連通群（參考：v1.1 主樣本 300 對只有 483 個不同 PR，117 個 PR 各出現兩次，連成 183 個群；全部候選的群會更大，群大小分布照實報告）。
- 不設每個 PR 的出現上限；相依性由 §8 的群集 bootstrap 處理。**「每個 PR 只用一次」只做敏感性分析，不是刪題（D3）**。決定性規則：在每個 `cluster_id` 內取題目 id 字典序最小的一題；再依這些代表題的 id 字典序做貪婪掃描，若與已保留題共用任一 PR 就跳過。連通群定義下，不同群的代表題不會共用 PR，貪婪步與「每群一題」等價，仍照這個順序寫死以便重現。

### 2.7 抽題工具的輸出（全部封存）

`items.jsonl`（每題：id、專案、集合、base、目標檔、各 patch 的 PR、patch 來源〔最終 head／rebase 前 head／三方合併〕、commit 時間、送出順序、hunk 範圍、分層、**寫入類別、語意旗標、測試目的、正確答案（期望 bytes 的 SHA-256 或「只落地一方」的允許結果集合）**、cluster_id、固定測試 ID 集）、`excluded.jsonl`（每個技術排除與理由碼）、`expected/`（期望檔案 bytes）、`summary.json`（各類別、各旗標、各專案的題數）、工具原始碼與凍結雜湊。

## 3. 多 session 模擬多個 agent

### 3.1 主體：獨立 OS 程序重播固定的真實 patch

- 每個模擬 agent＝**一個獨立的 OS 程序**（獨立 PID、獨立 Node runtime），各自從同一個 base 出發，送出它那一份固定的真實 patch。重播固定 patch 是為了決定性與可重現，並隔離「提交層是否正確」這個問題，不需要花模型費用。
- 所有程序共用同一個工作樹與**同一個收件匣＋批次協調器**，讓真實的多份 proposal 能在同一批、同一 base 上合成。

### 3.2 共用收件匣與批次協調器

- 以（目標檔、base hash）為鍵。第一份 proposal 到達時開窗；到 compose 窗結束（主要設定 100 ms）或達到批次上限時封批；封批後才到的 proposal 進下一批，對新的 base 重新合成。
- 每一批記錄：batch_id、base hash、成員 proposal、每份的到達時間、實際 batch size、合成判定、提交結果。
- **協調器屬於誰（D5，已決定）**：共用收件匣與批次協調器放在 **ATM core**。實作是另一個 PR（另一個 agent 進行中），不在本預先登記 generation 裡改 core。論文要主張「ATM 能做跨 agent 批次合成」，主跑的 steward 臂必須走該 core 機制。在該 PR 合併前，不得把 harness 私有協調器的結果寫成 ATM 產品已具備此能力；若該 PR 尚未合併就需要量測，只能標成「以 harness 協調器測量 composer」，且不得混進主要主張。開跑時把 core PR 的合併 SHA 寫進該 run generation 的 pins，不回寫本檔。
- 不再使用 v1.x harness 的「精確重新定位」：所有 proposal 都以共同 base 為準，後到者對新 base 的重新合成由 ATM（或各基線自己）負責，不由 harness 先代勞。

### 3.3 送出節奏：依原始 commit 順序，間隔是掃描變數

- 所有 agent 從同一 base 出發，依原始 commit 順序送出；相鄰兩份的**間隔是一個掃描變數**（已與文一確認，主跑全部題目都跑）：**0、50、100、500、2,000 ms**。
  - 100 ms＝主要 compose 窗的邊界；500 ms 是文一提出的 0.5 秒，保留為一個點。
  - **抖動（本版凍結的產生器）**：間隔 I 毫秒時，抖動為整數毫秒，離散均勻分布在 {0, 1, …, floor(min(10, 0.1×I))}（I＝0 時只有 0）。第 k 個相鄰間隔（k 從 0 起）的種子是 `sha256("hist-v2.0|jitter|{item_id}|{seed_index}|{interval_ms}|{order}|{k}")` 的前 8 位元組，小端解讀成 uint64，作為 PCG64 種子，再取 `integers(0, floor(span)+1)`。`order` 是 `commit` 或 `reverse`。同一題、同一 seed、同一間隔、同一順序可以逐 run 配對。
- **必須明說**：如果固定間隔 0.5 秒、compose 窗 100 ms，第二份 proposal 到達時第一批早已封批，batch size 永遠是 1，根本測不到合成。所以 500 ms 這一點的意義是「agent 到達很分散時 ATM 是否退化成和 file_lock 一樣的逐一提交」，不是合成能力的測試。每個間隔都報 batch size 分布。
- **兩種到達順序都要跑**：原始 commit 順序＋反向順序。3–4 份延伸組另加一個排列：種子 `sha256("hist-v2.0|perm|{item_id}|{seed_index}")` 前 8 位元組小端 uint64 的 PCG64，對送出順序做 Fisher–Yates。這個排列只屬於延伸組，不取代前兩種順序。
- **次要因素：compose 窗大小（D6，已決定）**：要做。窗長 0（不開窗）、100（主要）、500、1,000 ms，與五個送出間隔交叉。只在 dev 的 A、B、C **各 20 題**固定子集上跑。挑選規則：該寫入類別、`set=dev` 的題目依 id 字典序取前 20 題。某類別不足 20 題就全取，並在 run generation 記錄短少，不從其他類別補。這個子集只服務這個次要因素，主跑仍是全部題目。
- **次要變體（D7，已決定）**：commit 層級送出（PR 內每個 commit 各送一次，依時間交錯）只當次要，不進主要分母。主體是每個 PR 一份 patch。

### 3.4 之後的選配：小型真 LLM agent 臂（現在不做）

- 之後若論文要主張「真實 AI 協作效率」，再加一個小型補充臂：例如 10–20 道題、每題 2–3 個真 coding agent 由題目描述各自產生 patch，再走同一套收件與提交路徑。
- 此臂只當補充，不進主要分析，不影響本設計的凍結與執行。

## 4. 逐層記錄

每份 proposal 都記錄它停在哪一層、為什麼：

| 層 | 記錄 |
|---|---|
| admission（准入） | 是否通過、理由碼、等待時間 |
| inbox／batch | 到達時間、所屬 batch、batch size、是否晚到而進下一批 |
| compose（合成） | 合成判定（相容／衝突／需 steward）、衝突理由、重新合成次數 |
| commit（提交） | base 重驗結果（相同／hash drift）、寫入、ack 時間、收據終態 |

- 終態只有這幾種：`committed`、`rejected-conflict`、`rejected-hash-drift`（另列）、`rejected-admission`、`timeout`、`error`。恆等式「完成＋拒絕＋逾時＋錯誤＝總 proposal」逐 run 驗證。
- harness 本身造成的擋下另列，不算進 ATM 的判斷。

## 5. 公平的比較臂

| 臂 | 做法 |
|---|---|
| **steward（ATM）** | 准入 → 共用收件與批次 → `composeBrokerProposals` → `applyStewardPlan`（含提交時 base 重驗） |
| **file_lock** | 整檔鎖內：讀目前檔 → 以 `git merge-file`（目前、base、我的）合入 → 原子寫入 → 解鎖；衝突即拒 |
| **occ（修正後）** | 鎖外：讀目前檔與版本、算出候選；**提交時用短鎖（或真正的 CAS）把「重驗版本＋寫入」做成不可分割的一步**；版本不同就重試 |
| **git_three_way（修正後）** | 與 occ 相同的原子提交，但候選由 `git merge-file` 算出 |
| bare_composer（消融） | 與 steward 相同的合成與套用，但繞過准入；只做消融，不進主要比較 |

- **原子提交先驗證**：以可控的雙程序 barrier 測試（在「重驗之後、寫入之前」強制讓另一程序寫入），確認修正後的 occ 與 git_three_way 不再有檢查後被改寫的窗口；通過才進 pilot。
- **統一的等待與重試契約（D8，已決定；D2 不依題目大小放寬）**：所有臂（含 bare_composer 消融）相同。每份 proposal 期限 **30 秒**，不依 hunk 數或檔案大小縮放；超過記逾時並照實報告，大小只當共變數。最大重試 **8** 次。退避為指數退避，再加由 seed 決定的抖動：第 \(r\) 次重試（\(r\) 從 1 起）的基底等待是 \(\min(8,\ 2^{r-1})\) 秒，抖動為 0 到該基底的 10%（毫秒取整），種子 `sha256("hist-v2.0|retry|{item_id}|{seed_index}|{arm}|{interval_ms}|{order}|{proposal_index}|{r}")` 的前 8 位元組小端 uint64，PCG64。逾時不算拒絕，單獨列。
- **成本量測**（所有臂一樣）：正確完成量／秒、固定工作量的 makespan、每份 proposal 從送出到終態的延遲 p50／p95／p99／max（**包含被拒與逾時的**，不只算成功者）、鎖等待時間、重試次數、每程序 CPU 時間（getrusage）、峰值記憶體、拒絕與逾時數。分位數照論文 §5.5 的定義，不平均各 run 的 p95。
- 不把所有拒絕都說成「避免了錯誤」；只有標籤為衝突且最終檔案正確時，才算「正確拒絕」。

## 6. 修正後的語意評分器

### 6.1 觀測狀態

每個測試 ID 在每個條件下只能是：`pass`、`fail`、`skip`、`xfail`、`missing`（固定集合中的測試沒有被收集到）、`collection-error`、`unknown`（其他無法判定）。skip、xfail 不再算通過。

### 6.2 固定測試集與計算規則

- 每道題的測試 ID 集合在抽題時固定（兩個 PR 的 gold test patch 觸及的測試，在 gold 合併結果上收集）並封存；各條件一律跑同一個集合。
- 「合成後新壞掉」＝在 A 單獨、B 單獨、參考合併結果三方都**確實觀察到 `pass`**，而在 run 的最終檔案上觀察到 `fail`。任一方不是 `pass`，該測試記 `unknown`，不算 0。
- 最終 bytes 與參考答案相同時可重用參考答案的測試結果，但必須標成「位元相同、沿用」，與「實際重新執行」分開計數。

### 6.3 五種負控制（必須在冒煙測試中全部被抓到）

| 負控制 | 製造方式 | 評分器應給 |
|---|---|---|
| 整個測試模組消失 | 刪除固定集合中的一個測試模組 | `missing`，不是 pass |
| 收集失敗 | 在測試模組注入語法錯誤 | `collection-error` |
| 零測試 | 讓選擇器選不到任何測試 | `missing`／`unknown`，整題標不可評估 |
| skip／xfail | 對固定集合中的測試加上 skip 或 xfail 標記 | `skip`／`xfail`，不是 pass |
| 測試改名 | 把一個固定測試改名 | 舊 ID `missing`，新 ID 不在集合中、另列 |

另保留 v1.x 的寫入層植入故障（遺失與損毀），確認寫入 oracle 會抓到。任何一個負控制沒被抓到，就先修評分器、開新版本，再重跑冒煙測試。

- 既有 HIST v1.x 的表 R12：若原始 log 還在，以新評分器重評並另列；若不在，論文只把它當弱證據，不重寫舊 generation。

| 標籤＼結果 | 全部落地且 bytes 正確 | 只有一方落地、其他被乾淨拒絕 | bytes 與期望不同（混合） | 有 ack 但效果不見 | 檔案損毀 | 逾時／錯誤 |
|---|---|---|---|---|---|---|

## 8. 統計

- **推論單位是題目**，不是 run。同一題的 seeds、間隔、順序是重複量測。
- **主要報告單位是「類別 × 專案」**：每個寫入類別（A／B／C）分開報，類別內再依專案分層；整體數字以專案分層後合併，不讓題目多的專案主導。全部類別合併的總數只當次要。
- 語意終點只在旗標 S 的題目上報，旗標 N 的題目一律「不可評估」。
- **群集 bootstrap**：在每個專案內，以共用 PR 群（cluster_id）為單位重抽，B＝10,000，報 95% 百分位區間。
- **配對差值**：同一題、同一 seed、同一間隔、同一順序下，steward 與其他各臂的差（正確完成量／秒、延遲分位數、正確合併率、誤拒率），報差值的群集 bootstrap 區間。
- **主要分析圖**：橫軸為送出間隔（0／50／100／500／2,000 ms），縱軸為正確完成量／秒與延遲 p50／p95／p99，steward、file_lock、修正後 occ 與 git_three_way 各一條線，並疊上 steward 的 batch size 分布。這張圖要誠實顯示：在哪些間隔 ATM 的批次合成有幫助，在哪些間隔它與 file_lock 收斂，甚至較慢。
- **敏感性分析**：「每個 PR 只用一次」的決定性子集；只用單一 PR 群（群大小 1）的題；只用最終 head（不含 rebase 前 head 與三方合併放回的 patch）；逐一剔除專案；只用 O3／只用 O1+O2；抖動加大一倍；dev 與 held-out 分開。
- **不做勝出宣稱**：所有比較都是描述性的區間與差值；不以 p 值宣稱 ATM 較好。dev 與 held-out 結果分開報，held-out 只跑一次。

## 10. 凍結、封存與停止規則

- 每一個階段的輸入與輸出都是新的 generation，放在 `research/paper-v2/` 下並登記在 `EVIDENCE_INDEX.md`；封存後不可變，舊 generation 永不修改。

- 所有結果標「作者自行執行、未獨立重現」；CI 結果另列。**D9（已決定）**：論文寫明 HIST-v2 取代 Phase 3 的 450-run 主矩陣，並說明它涵蓋的研究問題（多寫入者批次合成、相容合併、衝突拒絕、與 file_lock 的代價對照）。不再把「450-run 未執行」當作 v2 的待辦。v1.x 與 r1–r6 generation 裡既有的「未執行」句子保持原樣，不回溯修改。
- 不 tag、不 npm publish。

## 12. 與 HIST v1.x 的差異一覽

| 問題 | v1.x | v2 |
|---|---|---|
| 跨寫入者批次合成 | 每程序 `expectedCount`＝1，batch size 恆為 1 | 共用收件與協調器，報 batch size 分布 |
| 同一 hunk | 停在 harness 重新定位（已過准入、未進 composer） | 不做 harness 重新定位，直接交給 composer |
| 選題 | 抽樣 300 對、試跑用過的排除 | **全部候選都測**；只做分類（A 不相交／B 同區可合併／C 真衝突／旗標 N 無可跑測試），只排除技術上跑不起來的 |
| 正確答案 | 只有寫入安全 oracle | 每題事先標測試目的與期望結果（git 合併 bytes 或「只落地一方」） |
| 結果呈現 | 全部配對合併報 | 依類別分開報，總數只當次要 |
| OCC／Git 基線 | 重驗與寫入之間有窗口 | 短鎖或 CAS 原子提交，barrier 先驗 |
| 等待／重試契約 | 各臂不同 | 統一 |
| file_lock 成本 | 未量 | 吞吐、延遲分位數、等待、重試、CPU、記憶體 |
| 語意評分 | skip／xfail 算通過、零測試未處理 | 七種觀測狀態、固定測試集、五種負控制 |
| 相依 | 按配對 bootstrap | 全部保留；按共用 PR 群 bootstrap，「每 PR 只用一次」只當敏感性子集 |
| 泛化 | 修正與驗證同一樣本 | 時間與專案 held-out，不共用 PR |
