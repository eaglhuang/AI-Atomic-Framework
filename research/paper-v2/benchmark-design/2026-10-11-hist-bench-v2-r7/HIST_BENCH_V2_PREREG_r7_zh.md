## 0. 這份修訂改了什麼

r6 的輸入種類隔離與全部拒絕規則維持不變。外部再審指出還有一個窄縫：jsonschema 4.18.0 的 Draft 2020-12 預設整數檢查接受 `1.0` 這類整數浮點，而跨欄位檢查若只認 Python `int`，比較會被跳過，純語意物件可能算出 2/1。本修訂把這一條定死（R7-D1）。摘要、下文與分類器 v7 使用同一套說法。r6 已經定下的兩條仍在：

1. 輸入種類隔離（R6-D1）。接受與語意評估不再共用一個 `oneOf`。`acceptanceEntry` 的 `kind` 必須是 `acceptance`，`semanticEntry` 的 `kind` 必須是 `semantic-evaluation`，兩邊 `additionalProperties` 都是 false。`validate_acceptance_input` 只驗證接受入口，`validate_semantic_input` 只驗證語意入口，`validate_score_instance` 只按 `kind` 走其中一個。混有 `retained_pass_count=2`、`reference_pass_count=1` 與合法接受欄位的物件，每一個入口都拒絕，不得算成 2/1。分類器其餘 schema（items、excluded）本來就不是兩種資料的聯集，沒有第二個這種分支。
2. 全部拒絕與矛盾紀錄（R6-D2）。安全上正確的全部拒絕（`full-reject-only-legal-outcome`）仍是安全通過，吞吐與進度計數是 0，不是 `combined_success` 的成功理由。時間終態已經終了時，若終態說已 ack 而接受紀錄說未 ack，或反過來，或兩邊的 `proposal_id` 不同，或終態記下的接受集合與接受紀錄不同，狀態是 `inconsistent`，不得算成功。

工作負載仍然是：全部候選都測、分類器只貼標、多個獨立程序送出真實 patch、間隔掃描 0／50／100／500／2,000 ms。兩份 proposal 的題目是短猝發，不是持續負載。不在這份修訂跑分類或臂。

## 1. 主張（都限定在寫明的檔案與故障模型裡）

檔案與故障模型：同一台 Linux 機器、同一個本地檔案系統上的單一文字檔；故障只含本設計列出的寫入遺失、混合位元組、假確認、逾時與工具錯誤。沒有涵蓋跨主機、網路檔案系統、斷電、多檔交易或程序被殺。在這個模型裡觀察到零次失敗，只是該次數下的觀察，不是保證。

| 主張 | 白話 | 分開報告的量 |
|---|---|---|
| **C1** | 在上述模型內，已確認（ack 時間落在期限內）的效果最後仍在檔案裡，檔案沒有多出、少掉或打亂的行 | 遺失效果數、損毀檔數、結構違規數，以及觀察次數。零次觀察用 §6 的分量上界，不寫成「不會發生」，也不叫做 proposal 失敗率 |
| **C2** | 相容的 proposal **可以在同一批被提交**。等待與吞吐分開報 | 同一批提交的正確批次數；等待時間；正確完成的 proposal／秒與效果／秒。相容題被拒是進度成本 |
| **C3** | 允許的結果是完整 proposal 的**每一個**合法子集，並標出哪些是極大。參考位元組是該子集自己的 R(S)，不是只留極大子集 | **安全**：S 合法且檔案等於 R(S)，沒有假確認。**進度**：S 是不是極大。接受合法但非極大的子集是進度不足，不是安全失敗 |

與 `git merge-file` 逐位元組相同，只表示符合該文字合併標準，不表示語意上較優。

## 2. 分類與留出集

全部候選都測。分類器 v7 只貼類別與答案，不跑臂。技術排除只有分類器 v7 規則列出的理由，每一筆都留理由碼。

共同 base 是全部 `mb` 的極大共同祖先（`git merge-base --octopus --all` 再取極大），不是一般多參數 `git merge-base`。多於一個最佳 base：技術排除 `multiple-best-common-bases`，記下理由並封存全數 SHA（R2-D1）。不私下挑一個。

`mergeable`、`true-conflict`、`tool-execution-error` 分開。非衝突的非零結束不得進 C。單邊無法落到共同 base 的是 `transplant-conflict`，不是並發衝突。

合法子集可以判定：子集裡每個 proposal 都可落地，而且對共同 base 的 `git merge-file` 在每一種順序都乾淨、位元組相同。答案鍵列出**全部**這種子集。每個子集有自己的 R(S)。`maximal=true` 表示沒有更大的合法子集包含它。可乾淨合併的題，整組是唯一的極大子集，較小的合法子集仍然列出。順序相依的整組不是合法子集。

合法子集的鍵（R4-D1）是排序後的唯一 proposal id，記在 `set_key`，`prs` 與它相同。提交時間較早的 PR 3 與較晚的 PR 1 組成的集合，鍵是 `[1, 3]`，不是 `[3, 1]`。產生器與 `score_run` 都用這把鍵。位元組若依順序而變，該排列另記在 `order`，不拿來查找合法子集。

安全評分器 `score_run` 吃臂的結果，不在評分時重跑分類。輸入欄位見 `schema/score-input.schema.json`：`accepted_prs`、`observed_sha256`、`acked`。`accepted_prs` 先收成上面的集合鍵再查找。

- S 合法、位元組等於 R(S)、而且有期限內 ack：安全通過。S 若不是極大，進度是不足。只接受 {A}、而 {A,B} 也合法，就是這種情形。
- S 不在合法清單、位元組不等於 R(S)、或空集合卻 ack 成功：安全失敗。
- 沒有 ack、檔案仍是 base：安全通過（沒有假接受）。若當時還有合法子集，進度是不必要拒絕。
- 類別 B 被 ATM 拒絕仍是進度成本，不得改標成 C。

2026-01-01～2026-09-30 稱為 **後期歷史留出集**（`later-period-historical-holdout`），不稱為未來資料。分群是 dev、跨窗、後期歷史留出集、專案留出集之間的共享 PR 連通分量，而且是傳遞的：(1,2)／(2,3)／(3,4) 是同一分量。相同補丁、cherry-pick、backport 另加邊。分量碰到 dev 的題不再是未看過的留出集。分量的鍵含專案，不跨專案相連。

**留出集一旦為了調參而檢視題目或答案，就不再是未看過的。** 封存分類結果本身可以做；用那些答案或類別計數去改 harness、評分器、門檻或臂，該分量就算被看過，不得再當留出集。

專案留出集加上 flask 與 requests。主跑 2 個 seed（R2-D4）。2 個 seed 只是有限重播，不是可重現性證明。

## 3. 期限、重試與各臂同一套提交

時鐘從**該 proposal 第一次送出**起算 30 秒。這 30 秒包含准入、批次窗等待、等鎖、計算與全部重試。重試不把時鐘歸零，也不另開 30 秒。

「8」的意思是 **8 次重試，不是 8 次總嘗試**（R2-D2）。第一次送出是嘗試 0，其後最多再試 8 次，合計最多 9 次嘗試。

計入這 8 次的：同一 proposal 因衝突、版本不符、CAS 失敗或鎖未取得而重新讀檔、重新合成或重新提交。同一次合成裡單次呼叫 `git merge-file`、同一次原子替換裡的單次 fsync，不另計一次。內部重新合成若做成另一次提交嘗試，那一次計入 8（R2-D3）。

各臂使用同一鎖範圍（整檔）、同一種原子替換（暫存檔、fsync、rename 覆蓋）與同一耐久性要求。ATM 臂要加上批次協調器與 SQLite 的耗時，這些耗時算在 30 秒裡，也算在等待與 CPU 裡，不從分母拿掉。

### 3.1 為什麼 occ 與 git 三方收成一條臂

r2 要求各臂同一把鎖、同一種原子替換，並且 occ 的候選也在讀到的版本上用 `git merge-file` 算出。版本不符只是把這同一套程序再跑一次。候選的產生方式、base、鎖範圍、重試上限都沒有剩下的差別，分成兩條臂只會把格子加倍，卻沒有可以解釋的對照。

因此主比較是三條臂（R3-D1）：

| 臂 | 候選怎麼產生 | base | 鎖 | 重試 |
|---|---|---|---|---|
| steward | ATM 批次協調器的合成 | 協調器綁定的不可變 base | 與其他臂相同的整檔鎖 | 同一套 8 次重試。協調器與 SQLite 的耗時計入 30 秒 |
| file_lock | 鎖內讀改寫該 proposal 的 hunk，不用 `git merge-file` | 鎖內讀到的檔案 | 同一把整檔鎖，持有到原子替換結束 | 同一套 8 次重試 |
| textual_merge_file | 鎖外用 `git merge-file` 把這份 proposal 折進當時讀到的檔案。不用 `--union`／`--ours`／`--theirs`。鎖內若 base 變了，這個鎖外候選作廢 | 鎖內重讀的檔案位元組。與鎖外不同就丟棄鎖外候選，在鎖內的 base 上重算 | 同一把整檔鎖。重讀、重算、rename 都在這把鎖裡 | 鎖內 base 變了而重算，計入 D8 的 8 次重試（R2-D2）。時鐘不歸零。重試已滿 8 次就停止，不得提交過期候選 |

`textual_merge_file` 仍是單一臂（R3-D1）。鎖內作廢並重算是這條臂的義務（R4-D2），不是把 occ 與 git 三方再拆開。base 沒變時，鎖外候選可以提交，這一次不另計重試；同一次原子替換裡的單次 fsync 仍不另計（R2-D3）。bare_composer 仍不進主比較。

主格仍是每題 60：2 個 seed × 2 個順序 × 5 個間隔 × 3 條臂。這條重算規則不增加臂，也不改 60。舊長矩陣的 720＋270＝990 也不改。

### 3.2 逾時：全部寫入者停止，然後對帳

任一 proposal 的 30 秒到期時，**該題的所有寫入者都停**。停止時刻記成 T_stop。停的意思是：不再送出、不再重試、不再開始新的提交。已經寫出暫存檔但還沒有 rename 的程序，要嘛在有效停止時刻前完成 rename 並留下時間戳，要嘛丟棄暫存檔、不 rename。

每份 proposal 的有效停止時刻是 min(自己的第一次送出 + 30 秒, T_stop)。晚送出的 proposal 不另得 30 秒。題目在 t＝0 開始、T_stop＝30、某份 proposal 在 t＝2 才送出，它的可執行時間是 28 秒。這個 28 秒要記下來。該 proposal 仍是一份送出，終態不是 success 時算 `submitted-not-success`，不從功能交付的分母拿掉，也不因為窗口較短就改記成功。

對帳在**每一個寫入進入點都已停止**之前不是終態。還有進入點活著時，終態是 `reconciliation-incomplete`，即使當時的 rename 與 ack 看起來像成功。確認全部進入點停止之後，才套用下表（R4-D3）。

| 觀察 | 終態 | 停止理由 | 怎麼計 |
|---|---|---|---|
| rename 與 ack 都在有效停止時刻以前 | 時間終態 `success`（`time_window_success`） | `acked-in-window` | 只完成時間這一半。`reconcile_terminal` 的 `in_throughput` 仍是假。要再滿足合法集合與位元組等於 R(S)，`combined_success` 才計入期限內吞吐（R5-D3） |
| rename 在有效停止時刻以前完成，ack 晚於該時刻 | `durable-unacked` | `ack-late` | 不計吞吐。不是 success，也不是 `late-commit-after-timeout`。進安全對帳 |
| rename 在有效停止時刻以前完成，沒有 ack | `durable-unacked` | `ack-missing` | 同上 |
| rename 晚於有效停止時刻 | `late-commit-after-timeout` | `rename-after-stop` | 不計吞吐。沒有期限內 ack 的，不自動算安全通過 |
| 沒有 rename，題目先停 | `timeout` | `item-stop` | 仍算一份送出。可執行時間是剩餘的那段 |
| 沒有 rename，自己的 30 秒先到 | `timeout` | `own-deadline` | 仍算一份送出 |
| ack 在期限內，但檔案不是 R(S) | 安全失敗 | `false-ack` 或 `unauthorized-bytes` | 不計吞吐 |
| 工具或程序錯誤 | `error` | `error` | 與逾時分開 |
| 還有寫入進入點活著 | `reconciliation-incomplete` | `entry-points-still-live` | 尚未終態，不進吞吐 |

每一份送出的 proposal 都要落在一個終態，並帶停止理由與 `executable_seconds`。恆等式要能對上送出總數。`durable-unacked` 與 `late-commit-after-timeout` 分開列，不併進 success。

吞吐不看時間終態單獨決定。`proposal_final_report` 呼叫 `reconcile_terminal`、`score_run`，再交給 `combined_success`。準時但位元組不是 R(S)、位元組正確但 `durable-unacked`、位元組正確但晚於停止才提交、準時但集合不合法、對帳尚未完成，都不計吞吐。沒有假接受的空拒絕，以及安全上正確的全部拒絕（`full-reject-only-legal-outcome`），都是安全通過，吞吐與進度計數是 0（R6-D2）。時間終態已終了而 ack 紀錄矛盾，或提案身份、接受集合不一致，狀態是 `inconsistent`，不得算成功。

### 3.3 臂的執行順序

正式跑之前先產生排程：在題目 × seed × 順序 × 間隔的格子上，哪一臂先跑要預先平衡，再在平衡約束內用該題 seed 打亂。不得每一格都讓 steward 先跑。

### 3.4 要報的數

吞吐是**正確完成的 proposal／秒**，以及另外的**正確完成的效果／秒**。批次數與實體寫入次數（rename／fsync）分開報，不叫做吞吐。等待時間另行報。`late-commit-after-timeout` 不計入這兩個吞吐。

## 4. 批次協調器的最低契約

協調器放在 ATM core（另開 PR）。harness 只送出與觀察，不預先挑子集。收件匣放在套用佇列之前，同一批的 proposal 不會被佇列拆開。

一批至少要能證明：兩個獨立程序的有效編輯出現在同一次合成裡，並且有提交證明。`batch size ≥ 2` 指這個事實，不是 harness 把兩份預先拼好。

| 契約 | 要求 |
|---|---|
| 綁定 | 倉庫、目標、不可變 base、權限與政策版本綁在一起 |
| 每份 proposal | 保留 actor、task、scope、ticket、validators；不得擴權 |
| 成員 | 封批後成員不可變；proposal id 去重；重送同一 id 是冪等的 |
| 當機 | 提交成功、ack 尚未寫出之後當機，重啟不得再寫一次，也不得把已提交說成沒提交 |
| 過期協調器 | 舊協調器復活時不得對新 base 提交舊批次 |
| 證明 | 見上文：兩個獨立程序、一次合成、一份提交證明 |
| 逾時 | 遵守 §3.2：該題所有寫入者停止，晚到的提交只進對帳 |

## 5. 評分

兩個終點分開，不合成一個百分比（R3-D2）。

**功能交付率。** 分母是有單獨參考測試的全部送出 proposal。分子是這些 proposal 裡，單獨參考上通過的測試在最終檔案上仍通過的提案數。合法拒絕的 proposal 留在分母裡，不算交付，這是進度成本。沒有單獨參考測試的 proposal 不進這個分母。

**已接受變更的語意保留。** 只評實際接受且有期限內 ack 的集合 S。參考是 R(S) 上通過的測試，不是各 proposal 單獨 gold 的聯集，也不是「整組都合併」的參考（除非 S 就是那個極大子集）。分子是這些測試在最終檔案上仍通過的次數，分母是 R(S) 上通過的次數。合法拒絕不進這個分母。R(S) 沒有通過的測試（`passing_test_ids` 為空）是不可評，理由 `no-passing-tests-on-R(S)`，不是保留率 0（R4-D5）。

輸入以分類器 v7 的 `schema/score-input.schema.json` 為準（R6-D1、R7-D1）。文件根不是實例入口，也沒有 `oneOf` 或 `anyOf`。接受入口與語意入口分開，各自要求 `kind`，並且拒絕未列出的欄位。`retained_pass_count` ≤ `reference_pass_count`，`retained_test_ids` ⊆ `passing_test_ids`，兩個清單裡的測試 ID 各自不得重複，兩個計數都 ≥ 0，而且計數等於對應清單的長度。計數必須是 Python `int`。`bool` 與 `1.0`、`2.0` 這類整數浮點在 `validate_semantic_input` 就被拒絕，不能經 `semantic_status` 進到 `delivery_rows` 變成 2/1。jsonschema 釘在 `4.18.0`。`passing_test_ids=["t1"]`、`reference_pass_count=1`、`retained_pass_count=2`，即使同時帶著合法的接受欄位，也是非法輸入。一般整數與 R(S) 沒有通過測試的情形仍照舊：後者是不可評，不是保留率 0。

另外三列，不併進上面兩個比率：

| 列 | 內容 |
|---|---|
| 合法拒絕 | 被拒絕、但某個合法子集仍包含該 proposal 的筆數。這是進度帳，不是安全失敗，也不進語意保留的分母 |
| 不可評（沒有通過的測試） | 功能交付：沒有單獨參考測試的 proposal。語意保留：R(S) 上沒有通過的測試，含 `has_reference_tests` 被誤標為真但通過數是 0。兩種都單獨計數，不寫成比率 0 |
| 零分母 | 可評筆數為 0 時，比率不計算，不寫成 0 或 1 |

原始測試事件保留：每個條件、每個測試 ID 一列，含原始狀態字串。

狀態對應：

| 觀察 | 記錄 | 不得記成 |
|---|---|---|
| 通過 | `pass` | |
| 失敗 | `fail` | |
| skip | `skip` | pass |
| xfail（有跑） | `xfail` | pass |
| `xfail(run=False)` | `xfail-not-run` | xfail 或 pass |
| 模組層級 skip | 該模組每個 ID 記 `module-skip`，另留一列模組事件 | pass |
| XPASS | `xpass`；若該次 pytest 把 XPASS 當成行程失敗，兩個事實都留 | pass 或 fail 的其中一邊 |
| 測試行程逾時 | `timeout` | fail 或 missing |
| 行程被殺 | `killed` | fail 或 missing |
| 日誌不在 | `log-missing` | pass |

固定集合以測試 ID 為準，各條件跑同一組 ID。

負控制必須打到**指名的測試 ID 與指名的狀態**，而不是只檢查「評分器有沒有響」。skip 與 xfail 分開測。另外要有：模組層級 skip、`xfail(run=False)`、XPASS 的解析。寫入層的遺失與損毀植入故障仍要被 oracle 抓到。安全評分器還要有契約測試：合法非極大子集是安全通過且進度不足；非法集合與位元組不符是安全失敗；不必要拒絕不是安全失敗。任一負控制沒被抓到，先改評分器、開新版本，再重跑冒煙測試。

## 6. 統計

同一題的 seed、到達順序與間隔綁在一起，重抽時整組帶走，不先對它們平均。它們不是獨立試驗，不能拿來當零事件上界的 n。

分量是共享 PR 連通分量，鍵含專案，所以分量不跨專案。在每個專案內以分量為單位重抽（B＝10,000）。

**跨專案的合併規則（R3-D5、R4-D4、R5-D1）。** 各專案先得到自己的估計。跨專案的點估計是這些估計的等權平均，權重事先固定為 1/K，K 是計畫裡的專案數，不讓題目多的專案主導。不把所有專案的分量放進同一個 bootstrap 樣本。

計畫內任一專案的分母為 0 時，跨專案的點估計與區間都是未定義。不把該專案刪掉，也不把其餘專案的權重改成 1/(K−1)。

原始點估計有定義、但某次 bootstrap 重抽的分母為 0 時，事先登記的政策是 `point-reported-interval-undefined`。點估計仍照原始樣本報告，因為它是觀察樣本的函數，一次分母為 0 的重抽不能把它抹掉。區間改為未定義，並寫出未定義重抽的次數與比例。不刪除該次重抽，不用其餘仍有定義的重抽去算百分位（那會改變估計對象，即使印出比例也算事後刪除），也不把權重改成 1/(K−1)。未定義不寫成 0。

這段、§0 與 `resample_final_report` 使用同一個政策識別字。原始樣本零分母與重抽零分母是兩種輸出，不混成「點估計一律未定義」。

獨立性是假設，不是從這份資料證明的：在一個專案內部，不同分量被當成這個上界的獨立單位。分量內部的 seed、順序、間隔不獨立。母體是該專案裡被觀察到的分量，不是「proposal 從無限母體抽出」，也不是跨專案的超母體。

比例用分量 bootstrap 的百分位區間。尾延遲在每一次重抽裡，用被抽中分量的原始 proposal 延遲重算 p95／p99，不先把各 run 的 p95 平均起來。

每份報告寫出不同 PR 數、分量數、最大分量占題目的比例。

**零事件（R3-D3）。** 某個專案裡、要估計的事件在全部分量都是 0 時，百分位 bootstrap 退化：每次重抽仍是 0，區間塌掉，不能寫成 [0, 0]，也不能把它當成已經估計出 0。這時改報單側 Clopper–Pearson 95% 上界，α＝0.05：

上界 = 1 − 0.05^(1/n)

n 是**該專案的共享 PR 連通分量數**。rule of three（約 3/n）只是 n 大時的近似，報告裡可以並列，但主上界是上面的精確式。n＝0 是零分母，不計算上界。各專案的上界分開列，不把多個專案的 0 加總成一個 n。這個上界的單位是分量，**不是 proposal 失敗率**。

不做勝出宣稱，不做以 p 值宣布 ATM 較好的檢定。2 個 seed 只表示有限重播。

## 7. 比較臂與 run 數

主比較臂從 r2 的四條收成三條：steward、file_lock、textual_merge_file。兩份 proposal 的主格是：

2 個 seed × 2 個順序（原序、反序）× 5 個間隔 × 3 條臂 = **每題 60**。

r2 若把 occ 與 git_three_way 分開，同一格是 2×2×5×4 = 每題 80。少掉的 20 是重複的那一條臂，不是少測題目。題數要等分類之後才知道，所以現在沒有單一的總 run 數。60 乘上主體兩份 proposal 的題數，才是主格的規模。

不進這個 60 的次要格：3–4 份 proposal 另加一個由 seed 決定的排列；compose 窗只在 A／B／C 各 20 題上當次要因素；「每個 PR 只用一次」只當敏感性子集；依 commit 拆開送是次要。bare_composer 不在主比較裡。這些都不加進 60。

舊的、尚未執行的長矩陣是另一套數字，HIST-v2 不跑它。論文草稿把 Phase 3 叫做 450-run，但同一份草稿的算式是 3 種工作負載 × 2 種拓撲 × 5 條主臂 × 10 個 seed × 3 次重啟 = 900，加上 3 條診斷臂只跑單程序 = 270，合計 1,170。那 5 條主臂是 lock、CAS／occ、Git、bare composer、完整 ATM。occ 與 Git 收成一條之後，主臂是 4 條：3×2×4×10×3 = **720**，診斷臂仍是 **270**，合計 **990**。480 個情境工作與 480 個故障 run 仍不同質，不加成這個數。r4 已執行的「E4 重播 450＝6 臂 × 75」是驗證回合，不是 Phase 3，HIST-v2 不取代它。

| 舊矩陣的軸 | HIST-v2 |
|---|---|
| 多寫入者對同一檔的合成與衝突 | **取代**（真實 PR 的短猝發） |
| 文字合併的合法子集、假接受與不必要拒絕 | **取代**（全部合法子集，安全與進度分開） |
| 與 file_lock、文字合併臂的同契約比較 | **保留為三條主臂**（steward、file_lock、textual_merge_file），在 HIST 題目上，不是在 1,000 次邏輯操作的長跑上 |
| cold／hot 工作負載 | **未涵蓋** |
| worker 數量伸縮（1×8 與 8×1） | **未涵蓋** |
| 持續負載（每 run 大量連續操作） | **未涵蓋**。兩份 proposal 是短猝發 |
| API／CLI 雙入口 | **未涵蓋** |
| 程序被殺、回滾、收據遺失 | **未涵蓋**（協調器契約要求當機後不雙寫，但本設計的主跑不執行這些切斷） |

已封存的 r1–r6 驗證數字保持原樣，不併進 HIST-v2 的分母。

## 8. 階段

| 階段 | 做法 |
|---|---|
| 0 分類 | 用分類器 v7 標全部候選。不跑臂。封存前不得拿答案調參 |
| 1 冒煙 | 很小的決定性子集，外加 §5 的負控制。封存結果後**停止**，不自動進入 pilot |
| 2 pilot | 使用者明確同意後才跑。試跑，不進正式結果 |
| 3 主跑 | 使用者明確同意後才跑 |
| 4 留出集 | 使用者明確同意後才跑，而且只在方法凍結之後。被檢視過的分量不得當作未見資料 |

找到 bug 就開新版本，不在原封存上修。steward 在期限內出現遺失、損毀或假接受，跑完當前批次、凍結、停下、照實寫。不宣稱勝出。不 tag、不 npm publish。

## 9. 仍沿用的執行骨架

- 一個模擬 agent 是一個獨立 OS 程序，重播固定的真實 patch。
- 間隔 0／50／100／500／2,000 ms，另加均勻抖動 0～min(10 ms, 間隔的 10%)，由 seed 決定。500 ms 與 2,000 ms 預期批次變小，用來描述等待與退化，不是合成能力的主證據。
- 原始 commit 順序與反向順序都跑。3–4 份的延伸組另加一個由 seed 決定的排列，延伸組是次要。
- compose 窗大小只在 A／B／C 各 20 題的固定子集上當次要因素。
- 「每個 PR 只用一次」只當敏感性子集。
- 每個 PR 一份 patch 是主體；依 commit 拆開送是次要。
- 比較臂是 steward、file_lock、textual_merge_file。bare_composer 不進主比較。
- 逾時遵守 §3.2。
- 原子提交先用雙程序 barrier 檢查「重驗之後、寫入之前」沒有窗口。通過才有資格進 pilot，而且 pilot 仍要另一次同意。
