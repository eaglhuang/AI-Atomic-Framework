## 0. 這份修訂改了什麼

上一稿的主張寫成「不必排隊」，C3 把衝突收成「只有一方落地」，期限與「8 次」沒有定義時鐘與計次，語意評分把通過收成三方交集，統計把同一題的 seed／順序／間隔拆開，也把「0 失敗」寫成好像已經證明。本修訂把這些收斂成可執行的契約。工作負載仍然是：全部候選都測、分類器只貼標、多個獨立程序送出真實 patch、間隔掃描 0／50／100／500／2,000 ms。

兩份 proposal 的題目是短猝發，不是持續負載。

## 1. 主張（都限定在寫明的檔案與故障模型裡）

檔案與故障模型：同一台 Linux 機器、同一個本地檔案系統上的單一文字檔；故障只含本設計列出的寫入遺失、混合位元組、假確認、逾時與工具錯誤。沒有涵蓋跨主機、網路檔案系統、斷電、多檔交易或程序被殺。在這個模型裡觀察到零次失敗，只是該次數下的觀察，不是保證。

| 主張 | 白話 | 分開報告的量 |
|---|---|---|
| **C1** | 在上述模型內，已確認（ack 時間落在期限內）的效果最後仍在檔案裡，檔案沒有多出、少掉或打亂的行 | 遺失效果數、損毀檔數、結構違規數，以及觀察次數。零次觀察要配上界（§6），不寫成「不會發生」 |
| **C2** | 相容的 proposal **可以在同一批被提交**。等待與吞吐分開報，不把「沒有排隊」寫進主張 | 同一批提交的正確批次數；等待時間；正確完成的 proposal／秒與效果／秒。相容題被拒是進度成本 |
| **C3** | 允許的結果是完整 proposal 的合法子集（3–4 份只取極大相容子集）。沒有任何合法子集時，才允許全部拒絕且 base 不變 | **假接受**（安全：不該落地的混進去、或 ack 了沒寫入）與 **不必要拒絕**（進度：仍相容的 proposal 被拒）分開計。B 類被 ATM 拒絕仍是進度成本，不得改標成 C |

與 `git merge-file` 逐位元組相同，只表示符合該文字合併標準，不表示語意上較優。

## 2. 分類與留出集

全部候選都測。分類器只貼類別與答案，不跑臂。技術排除只有分類器 v2 規則列出的理由，每一筆都留理由碼。

共同 base 是全部 `mb` 的極大共同祖先（`git merge-base --octopus --all` 再取極大），不是一般多參數 `git merge-base`。多於一個最佳 base：技術排除 `multiple-best-common-bases`，並封存全數 SHA。本修訂採用這個排除，不私下挑一個。

`mergeable`、`true-conflict`、`tool-execution-error` 分開。非衝突的非零結束不得進 C。單邊無法落到共同 base 的是 `transplant-conflict`，不是並發衝突。

C 的答案鍵是允許的完整 proposal 子集。安全＝結果是其中一個允許子集，且沒有假確認、沒有未授權的混合。進度＝仍可一起提交的 proposal 被拒。

2026-01-01～2026-09-30 稱為 **後期歷史留出集**（`later-period-historical-holdout`），不稱為未來資料。分群是 dev、跨窗、後期歷史留出集、專案留出集之間的共享 PR 連通分量，而且是傳遞的：(1,2)／(2,3)／(3,4) 是同一分量。相同補丁、cherry-pick、backport 另加邊。分量碰到 dev 的題不再是未看過的留出集。

**留出集一旦為了調參而檢視題目或答案，就不再是未看過的。** 封存分類結果本身可以做；用那些答案或類別計數去改 harness、評分器、門檻或臂，該分量就算被看過，不得再當留出集。

工作假設（上一輪決定，本修訂先採用，仍列在 §12 待確認）：專案留出集加上 flask 與 requests；主跑 2 個 seed。2 個 seed 只是有限重播，不是可重現性證明。

## 3. 期限、重試與各臂同一套提交

時鐘從**該 proposal 第一次送出**起算 30 秒。這 30 秒包含准入、批次窗等待、等鎖、計算與全部重試。重試不把時鐘歸零，也不另開 30 秒。

「8」在本修訂的意思是 **8 次重試，不是 8 次總嘗試**。第一次送出是嘗試 0，其後最多再試 8 次，合計最多 9 次嘗試。

計入這 8 次的：同一 proposal 因衝突、版本不符、CAS 失敗或鎖未取得而重新讀檔、重新合成或重新提交。同一次合成裡單次呼叫 `git merge-file`、同一次原子替換裡的單次 fsync，不另計一次。實作若把內部重新合成做成另一次提交嘗試，那一次要計入 8。

各臂使用同一鎖範圍、同一種原子替換（暫存檔、fsync、rename 覆蓋）與同一耐久性要求。ATM 臂要加上批次協調器與 SQLite 的耗時，這些耗時算在 30 秒裡，也算在等待與 CPU 裡，不從分母拿掉。

### 3.1 OCC 候選重算

1. 鎖外讀目前檔案與版本（內容 SHA-256，或協調器給的 base id）。
2. 候選只在這次讀到的版本上用 `git merge-file` 算出。版本在寫入前變了，這個候選作廢。
3. 取得與其他臂相同範圍的短鎖。
4. 鎖內重讀版本。與步驟 1 不同就放開鎖，這次算一次重試，回到步驟 1。
5. 相同才在**同一把鎖內**做原子替換，然後放開鎖並 ack。重驗與寫入之間不得放鎖。

### 3.2 逾時之後的寫入

成功的定義是：ack 時間 ≤ 第一次送出 + 30 秒，且效果在檔案裡。期限之後才耐久化的寫入記 `late-commit-after-timeout`，不計入期限內的成功，也不計入吞吐。沒有期限內 ack 的耐久寫入要單獨對帳，因為它可能是安全問題（寫了但沒有及時確認）。

### 3.3 臂的執行順序

正式跑之前先產生排程：在題目 × seed × 順序 × 間隔的格子上，哪一臂先跑要預先平衡，再在平衡約束內用該題 seed 打亂。不得每一格都讓 steward 先跑。

### 3.4 要報的數

每一份送出的 proposal 都要有終態：`success`、`blocked`、`timeout`、`error`，或期限到了仍在等的 `full-wait`。恆等式要能對上送出總數。

吞吐是**正確完成的 proposal／秒**，以及另外的**正確完成的效果／秒**。批次數與實體寫入次數（rename／fsync）分開報，不叫做吞吐。等待時間另行報。

## 4. 批次協調器的最低契約

協調器放在 ATM core（另開 PR）。harness 只送出與觀察，不預先挑子集。收件匣放在套用佇列之前，同一批的 proposal 不會被佇列拆開。

一批至少要能證明：兩個獨立程序的有效編輯出現在同一次合成裡，並且有提交證明。`batch size ≥ 2` 指這個事實，不是 harness 把兩份預先拼好。

| 契約 | 要求 |
|---|---|
| 綁定 | 倉庫、目標、不可變 base、權限與政策版本綁在一起 |
| 每份 proposal | 保留 actor、task、scope、ticket、validators；不得擴權 |
| 成員 | 封批後成員不可變；proposal id 去重；重送同一 id 是冪等的 |
| 當機 | 提交成功、ack 尚未寫出之後當機，重啟不得再寫一次，也不得把已提交說成沒提交 |
| 過期協調器 | 舊協調器復活時不得對新 base 提交舊批次 |
| 證明 | 見上文：兩個獨立程序、一次合成、一份提交證明 |

## 5. 評分

主要終點是**逐 proposal 的功能保留**：在「只有這份 patch 的參考結果」上通過的測試 ID，在最終檔案上仍通過的比例。次要終點才是三方都通過的交集（A 單獨、B 單獨、參考合併都通過，且最終仍通過）。

原始測試事件保留：每個條件、每個測試 ID 一列，含原始狀態字串。

狀態對應：

| 觀察 | 記錄 | 不得記成 |
|---|---|---|
| 通過 | `pass` | |
| 失敗 | `fail` | |
| skip | `skip` | pass |
| xfail（有跑） | `xfail` | pass |
| `xfail(run=False)` | `xfail-not-run` | xfail 或 pass |
| 模組層級 skip | 該模組每個 ID 記 `module-skip`，另留一列模組事件 | pass |
| XPASS | `xpass`；若該次 pytest 把 XPASS 當成行程失敗，兩個事實都留 | pass 或 fail 的其中一邊 |
| 測試行程逾時 | `timeout` | fail 或 missing |
| 行程被殺 | `killed` | fail 或 missing |
| 日誌不在 | `log-missing` | pass |

固定集合以測試 ID 為準，各條件跑同一組 ID。

負控制必須打到**指名的測試 ID 與指名的狀態**，而不是只檢查「評分器有沒有響」。skip 與 xfail 分開測。另外要有：模組層級 skip、`xfail(run=False)`、XPASS 的解析。寫入層的遺失與損毀植入故障仍要被 oracle 抓到。任一負控制沒被抓到，先改評分器、開新版本，再重跑冒煙測試。

## 6. 統計

同一題的 seed、到達順序與間隔綁在一起，重抽時整組帶走，不先對它們平均。

在每個專案內，以整個共享 PR 分量為單位重抽（B＝10,000）。專案權重事先固定為各專案相等，不讓題目多的專案主導。

比例用分量 bootstrap 的百分位區間。尾延遲在每一次重抽裡，用被抽中分量的原始 proposal 延遲重算 p95／p99，不先把各 run 的 p95 平均起來。

每份報告寫出不同 PR 數、分量數、最大分量占題目的比例。

零次失敗不得寫成區間 [0, 0]。獨立試驗的粗上界用 rule of three（0 次事件、n 次試驗時，約 95% 上界為 3/n）。試驗不獨立時，n 用分量數，並同時報分量 bootstrap 的上界。兩種上界都寫出來。2 個 seed 只表示有限重播。

不做勝出宣稱，不做以 p 值宣布 ATM 較好的檢定。

## 7. 與舊主矩陣的涵蓋

論文草稿裡有兩套未被執行、卻被當成同一件事的數字：

- 多處把 Phase 3 主矩陣叫做 **450-run**。這個名字沒有對上同一份草稿裡的算式。
- 同一份草稿建議的最小主矩陣是 3 種工作負載 × 2 種拓撲 × 5 條主臂 × 10 個 seed × 3 次重啟＝**900**，加上 3 條診斷臂只跑單程序＝**270**，合計 **1,170**。另外還有 480 個情境工作與 480 個故障 run，三者不同質，本來就不該加成一個樣本數。
- r4 已執行的「E4 重播 450＝6 臂 × 75」是驗證回合，不是 Phase 3，HIST-v2 不取代它。

下文「舊主矩陣」指尚未執行的 900＋270（以及被誤稱為 450-run 的那一塊）。HIST-v2 取代的是其中「多個寫入者同時改同一檔」的合成與拒絕問題，不取代下表裡標成未涵蓋的軸。

| 舊矩陣的軸 | HIST-v2 |
|---|---|
| 多寫入者對同一檔的合成與衝突 | **取代**（真實 PR 的短猝發） |
| 文字合併的正確子集、假接受與不必要拒絕 | **取代**（以合法子集計） |
| 與 file_lock、修正後 OCC、git 三方的同契約比較 | **保留為臂**，但是在 HIST 題目上，不是在 1,000 次邏輯操作的長跑上 |
| cold／hot 工作負載 | **未涵蓋** |
| worker 數量伸縮（1×8 與 8×1） | **未涵蓋** |
| 持續負載（每 run 大量連續操作） | **未涵蓋**。兩份 proposal 是短猝發 |
| API／CLI 雙入口 | **未涵蓋** |
| 程序被殺、回滾、收據遺失 | **未涵蓋**（協調器契約要求當機後不雙寫，但本設計的主跑不執行這些切斷） |

已封存的 r1–r6 驗證數字保持原樣，不併進 HIST-v2 的分母。

## 8. 階段

| 階段 | 做法 |
|---|---|
| 0 分類 | 用分類器 v2 標全部候選。不跑臂。封存前不得拿答案調參 |
| 1 冒煙 | 很小的決定性子集，外加 §5 的負控制。封存結果後**停止**，不自動進入 pilot |
| 2 pilot | 使用者明確同意後才跑。試跑，不進正式結果 |
| 3 主跑 | 使用者明確同意後才跑 |
| 4 留出集 | 使用者明確同意後才跑，而且只在方法凍結之後。被檢視過的分量不得當作未見資料 |

找到 bug 就開新版本，不在原封存上修。steward 在期限內出現遺失、損毀或假接受，跑完當前批次、凍結、停下、照實寫。不宣稱勝出。不 tag、不 npm publish。

## 9. 仍沿用的執行骨架

- 一個模擬 agent 是一個獨立 OS 程序，重播固定的真實 patch。
- 間隔 0／50／100／500／2,000 ms，另加均勻抖動 0～min(10 ms, 間隔的 10%)，由 seed 決定。500 ms 與 2,000 ms 預期批次變小，用來描述等待與退化，不是合成能力的主證據。
- 原始 commit 順序與反向順序都跑。3–4 份的延伸組另加一個由 seed 決定的排列，延伸組是次要。
- compose 窗大小只在 A／B／C 各 20 題的固定子集上當次要因素。
- 「每個 PR 只用一次」只當敏感性子集。
- 每個 PR 一份 patch 是主體；依 commit 拆開送是次要。
- 比較臂仍是 steward、file_lock、修正後的 occ、修正後的 git 三方，以及不進主比較的 bare composer。
- 原子提交先用雙程序 barrier 檢查「重驗之後、寫入之前」沒有窗口。通過才有資格進 pilot，而且 pilot 仍要另一次同意。
