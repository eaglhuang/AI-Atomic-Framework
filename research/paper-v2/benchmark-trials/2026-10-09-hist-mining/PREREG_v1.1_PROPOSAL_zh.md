## 1. 問題
- 照凍結規則（只把 base 改回 prereg 的合併 commit 公式），六個專案合計只有 7 個 O1，其中 6 個是兩邊修改完全相同，**真正改法不同的只有 1 個**（SymPy）。Django、xarray、pytest、FastAPI 都是 0。
- prereg §1.4 說「同一 hunk」分層是寫入安全最需要測的情況，目前等於沒有真實樣本。
- 原因：drift 排除的 1,205 對裡，1,164 對（96.6%）是「後合併的 PR 在合併前已經 rebase 到對方之上」，衝突在合併前就被作者解掉了，所以最終 head 不會在共同 base 上重疊。

## 3. 建議的規則文字（v1.1 只改這些）
1. **§3.1(4) 增加 4a**：如果配對中一方 X 的 `mb_X` 已經包含對方 Y 的合併 commit（Y 在 X 的 base 之前就合併了），而且照現行規則被判為 `drift`，就改用 X 的「合併前 head」h'：
   - 候選來源：X 的每一個 `HeadRefForcePushedEvent.beforeCommit`（時間用事件時間）、X 的每一個 PR commit，以及 X 裡每一個 merge commit 的第一個 parent（時間用 committedDate）。
   - 選擇：時間不晚於 `Y.merged_at`、而且不包含 Y 合併 commit 的候選中，時間最晚的一個。
   - `mb' = merge-base(h', landing_Y^1)`；X 的 code patch = `diff(mb', h')`。檔案分類、1–12 個原始碼檔、400 行上限照舊。
   - 其餘照舊：`b = merge-base(mb_Y, mb')`，兩個 patch 都要能無 fuzz 套用到 b，依 hunk 距離分 O1／O2／O3。
2. **新增配對標籤**（只描述，不影響分層）：`writer_version = final | pre-rebase`、`o1_kind = identical | divergent`。
3. **抽樣**：仍是每專案 50 對、每 PR 最多 2 對、O1→O2→O3 補位、種子 PCG64(20261008)。預期 O1 在 SymPy、xarray、Sphinx 接近或達到配額 17；Django、pytest、FastAPI 只有 6–8 個，其餘由 O2、O3 補位，補了多少照實記錄。
4. **語意終點**：pre-rebase 版本不是最終合併的程式碼，它的 F2P 測試沒有定義。這類配對**只算寫入安全終點**（完成、遺失效果、被擋、損壞檔），語意終點標「不可評估」。
5. **O1 相同修改**：兩邊都 `applied` 時，同樣內容出現兩次就是錯誤；正確結果是只出現一次。oracle 照現行 `overlap_both_applied` 逐筆鑑識，另外列子類。

## 4. 影響與限制
- 主跑規模不變：300 對 × 5 arm × 5 seed = 7,500 runs，加上舊 pin 1,500 和 O0 750，合計約 9,750 runs。
- 限制：h' 是 PR 在歷史上真的存在過的狀態，但不一定是作者最後想要的版本；force-push 事件的時間只是近似。論文要寫明 O1 樣本來自 rebase 前的版本。
- 不選 P 的替代方案：維持 v1.0，O1 只有 1 個改法不同的真實配對；論文照實寫「真實歷史 PR 在共同 base 上幾乎沒有同 hunk 衝突」，同 hunk 情況只由植入故障和先前的 E4／barrier 世代涵蓋。
